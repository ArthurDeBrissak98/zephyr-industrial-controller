# Контроллер на Zephyr и QEMU

Демонстрационный проект: эмулируем датчик 4–20 мА, управляем заданием частоты и проверяем, как контроллер реагирует на обрыв. Всё запускается в QEMU на `qemu_cortex_m3` — эмуляции ARM Cortex-M3, TI LM3S6965. В дальнейшем хочу перенести ту же логику на реальную плату.

Главный сценарий простой: запускаем привод, подаём обрыв датчика и получаем останов с записью причины в журнал. После восстановления сигнала авария остаётся зафиксированной. Её нужно сбросить вручную, а затем отдельно дать команду пуска.

## Как работает

После загрузки частота равна нулю. Когда приходит первый нормальный отсчёт, контроллер переходит из `STOPPED` в `READY` и ждёт `start`. Во время работы ПИ-регулятор задаёт частоту от 0 до 50 Гц. Шаг ограничен: не больше 1 Гц за цикл.

После каждого цикла опроса поток ждёт 100 мс; время обработки добавляется к этому интервалу. Если ток падает ниже 3,6 мА, контроллер переходит в `FAULT` и сразу обнуляет выход. Плавный останов в этом случае не применяется. Команда `stop` не снимает аварию, а `reset` не принимается, пока причина не устранена.

Есть два профиля: насос (`pump`) и приточка (`ahu`). Пока привод остановлен и нет зафиксированной аварии, можно сменить профиль и выбрать вход `4-20ma` или `0-10v`. Для входа напряжения команда имитации обрыва токовой петли отклоняется.

### Время расчёта PI и доступ из потоков

PI учитывает фактическое время между вызовами `controller_update`: ошибка умножается на `dt` в миллисекундах. Последняя временная метка хранится в `last_update_ms`. При инициализации она равна нулю, при успешном пуске, сбросе аварии и переконфигурации устанавливается в `now_ms`. При нулевом или отрицательном `dt` интегратор не меняется. В конце каждого вызова, включая обработку аварии, `last_update_ms` получает переданный `now_ms`. Время остановки не накапливается после нового пуска.

Интегратор хранится в `int64_t`, в единицах «ошибка × мс», с насыщением ±10000000. Проверка насыщения выполняется до умножения, поэтому большой интервал не вызывает переполнение. Коэффициент интегральной части приведён к прежнему периоду 100 мс: при штатном цикле отклик сохраняется. Ограничения выхода прежние — 0–50 Гц и не больше 1 Гц за вызов.

Параметры PI хранятся в `controller_config.pid`: `bias_x100=2500`, `kp=50`, `ki=5`, `divisor=10` по умолчанию. Смещение задаётся в сотых долях Гц. В `controller_configure` коэффициенты проверяются: `kp` и `ki` неотрицательные, делитель положительный, смещение в диапазоне 0–5000. При смене только профиля или входа нужно сохранить текущие `pid` из конфигурации.

У интегратора есть условное накопление: если рассчитанное задание достигает 5000 при положительной ошибке либо 0 при отрицательной, новое значение интеграла не сохраняется. Обратная ошибка позволяет уменьшать накопленный интеграл. Ограничения частоты и шага остаются прежними.

`controller_update` вызывается из потока `main`: после каждого цикла он ждёт 100 мс. Это номинальный период; PI использует фактическое время между вызовами. Команды `start`, `stop`, `reset`, настройка и операции NVS выполняются в потоке Shell. Порядок захвата: замок приложения → мьютекс контроллера → замок хранилища. При переносе на плату драйвер может принимать данные в ISR, но вызывать API контроллера нужно из потока, например через очередь сообщений.

В `struct controller` находится мьютекс Zephyr. Функции изменения состояния и чтения журнала берут его внутри. Приложение держит тот же мьютекс при копировании статуса и обмене с эмулятором, а внешний замок приложения объединяет чтение входа, расчёт и запись выхода в одну операцию. Мьютексы Zephyr допускают повторный захват своим потоком. `controller_init` нужно вызывать до запуска рабочих потоков; повторная инициализация допустима только при отсутствии обращений к контроллеру.

## Обработка датчика

Контроллер получает от входа ток в мкА или напряжение в мВ. По этому значению рассчитывается измерение для регулятора:

| Вход | Насос | Приточка |
|---|---|---|
| 4–20 мА | 0–100% | −20…+40 °C |
| 0–10 В | 0–100% | −20…+40 °C |

Все расчёты целочисленные. В `status` поле `scaled_x10` показывает пересчитанное значение, а `measured_x10` — среднее по четырём последним отсчётам. Оба поля в десятых долях: `500` для насоса — это 50%, `-150` для приточки — −15 °C. На старте усредняются только уже полученные отсчёты, без заполнения окна нулями.

Для токового входа допустим диапазон 3,6–21 мА. Участки 3,6–4 мА и 20–21 мА считаются допустимыми, но при пересчёте ограничиваются нижним и верхним значением шкалы. Ниже 3,6 мА фиксируется обрыв (`0x1`), выше 21 мА — выход за диапазон (`0x2`). Для входа напряжения допустимы только 0–10 В включительно; выход в любую сторону даёт `0x2`.

Проверка диапазона идёт до усреднения: один аварийный отсчёт обнуляет команду приводу в том же такте обработки. Контроллер не ждёт заполнения окна фильтра или задержек технологических защит. Сам отсчёт не попадает в фильтр. После восстановления входа или смены настроек история фильтра очищается. Пока `signal_valid=no`, значения измерения не используются для регулирования.

Показания можно задать вручную через Shell. Например, для входа 4–20 мА:

```text
inject signal 12000
status
inject signal 22000
status
events
inject signal off
reset
```

`12000` — нормальные 12 мА, `22000` — выход за верхнюю границу. После каждой смены сигнала подождите хотя бы один цикл опроса; для установления среднего — четыре. На входе 0–10 В та же команда принимает мВ, например `inject signal 5000`. `off` возвращает обычную модель датчика. Если отдельно включён `inject wire-break on`, он имеет приоритет: сначала отключите его.

### Что видно в диагностике

В `status` остаются числовые маски `active`, `latched` и `warnings`. Рядом выводятся их расшифровки: `active_names`, `latched_names`, `warning_names`. Если причин несколько, они перечисляются через запятую; если нет — `none`.

`filter_samples` показывает, сколько отсчётов накоплено в фильтре. `measurement_unit` указывает единицы обработанного значения: `percent_x10` для насоса и `celsius_x10` для приточки. При `signal_valid=no` измерение нельзя считать рабочим, даже если числовое поле равно нулю.

Ручная подмена видна по `signal_injected=yes`, заданному `injected_value` и единицам `injected_unit`. Отдельно выводится `wire_break_injected`. Включённая имитация обрыва имеет приоритет перед ручным значением тока. После `inject signal off` источник снова переключается на модель датчика. Команда подтверждает принятие настройки сразу, а сами показания обновляются на следующем опросе.

В журнале после строки события выводятся его профиль, тип входа, исправность сигнала и названия причин. Это данные на момент события: последующая смена профиля или типа входа старую запись не меняет.

## Предупреждения и технологические защиты

Кроме исправности электрического входа контроллер проверяет само измерение: уровень насоса или температуру приточки. Есть четыре ограничения: `low-warning`, `high-warning`, `low-trip` и `high-trip`. Каждое имеет порог, гистерезис и задержку.

Предупреждение не меняет состояние и не останавливает привод. Оно появляется в `warnings` и в журнале как `WARNING`; после возврата в норму снимается автоматически с событием `WARNING_CLEARED`. Бит `0x1` означает нижнее предупреждение, `0x2` — верхнее. Эти биты относятся к отдельной маске предупреждений, а не к `active` и `latched`.

Авария переводит контроллер в `FAULT` и обнуляет выход. Нижнее ограничение имеет код `0x4`, верхнее — `0x8`. Причина снимается после возврата за границу гистерезиса, но авария остаётся в `latched` до ручного сброса. Сброс не запускает привод. С предупреждением пуск разрешён, с зафиксированной аварией — нет.

По умолчанию установлены такие параметры:

| Ограничение | Насос: порог / гистерезис | Приточка: порог / гистерезис | Задержка |
|---|---|---|---|
| Нижнее предупреждение | 10% / 2% | 5 °C / 1 °C | 500 мс |
| Верхнее предупреждение | 90% / 2% | 35 °C / 1 °C | 500 мс |
| Нижняя авария | 5% / 2% | 0 °C / 1 °C | 1000 мс |
| Верхняя авария | 95% / 2% | 38 °C / 1 °C | 1000 мс |

Для нижнего ограничения отсчёт задержки начинается при значении **не выше** порога. Если до срабатывания значение вернулось выше порога, таймер обнуляется. Уже сработавшее ограничение снимается при `порог + гистерезис`. Для верхнего ограничения всё зеркально: срабатывание при значении **не ниже** порога, снятие при `порог − гистерезис`. При нулевом гистерезисе для снятия нужно строго перейти на нормальную сторону порога.

Задержка считается по времени, а не по числу отсчётов. Проверка идёт по отфильтрованному измерению, поэтому сначала учитывается время установления фильтра. Обрыв и недопустимый ток или напряжение по-прежнему останавливают привод немедленно, без этих задержек. Неисправный вход прерывает незавершённые таймеры; уже активное ограничение снимается только по следующему исправному измерению.

Ограничения проверяются и в `READY`, и во время работы, и в `FAULT`. Это позволяет увидеть предупреждение до пуска и проверить исчезновение причины перед сбросом.

Настройки доступны через Shell, когда контроллер остановлен и нет зафиксированной аварии:

```text
protect show
protect set low-warning 450 20 300
protect set low-trip 400 20 800
protect disable high-warning
```

После имени идут порог в десятых долях, гистерезис в тех же единицах и задержка в мс. Здесь нижнее предупреждение настроено на 45%, гистерезис 2%, задержку 300 мс. Нижняя авария — на 40%, 2% и 800 мс. `set` также включает отключённое ограничение. Порог и граница снятия должны помещаться в шкалу профиля, задержка — в диапазон 0–60000 мс. Нулевая задержка означает срабатывание на первом подходящем отсчёте.

Пары уставок проверяются независимо: нижняя аварийная уставка должна быть строго ниже верхней аварийной, нижнее предупреждение — строго ниже верхнего предупреждения. Равенство и пересечение возвращают `-EINVAL`, настройки при этом не меняются. Проверка действует и для отключённых ограничений.

Изменения настроек сначала действуют только в RAM. Чтобы они пережили перезапуск, выполните `config save`. Смена профиля восстанавливает его значения защит по умолчанию; смена типа входа сохраняет настройки, но сбрасывает таймеры и фильтр.

## Сохранение настроек в NVS

На `qemu_cortex_m3` используется Zephyr Settings с backend NVS. Для эмулятора добавлена отдельная flash на semihosting: её содержимое находится в файле `controller_flash.bin` в рабочем каталоге QEMU. Программа и её flash-хранилище разделены; файл настроек не записывается поверх прошивки.

```text
config show
config save
config load
config erase
```

`save` сохраняет текущий профиль, тип входа, параметры PI и все четыре настройки защит, включая признаки отключения. Автоматической записи при каждом изменении нет. `load` загружает сохранённый набор целиком. `erase` удаляет запись из NVS, но оставляет текущие настройки в RAM; после следующего запуска будут дефолты. Все три команды разрешены только в `STOPPED` или `READY`.

При загрузке программы сохранённые настройки читаются автоматически. Привод остаётся остановленным и по-прежнему ждёт `start`. Аварии, журнал, интегратор, таймеры защит и инъекции не сохраняются.

Формат записи имеет версию и CRC32. В NVS сохраняется один блок: профиль, вход, PI и защиты. До применения проверяются длина, версия, контрольная сумма, коэффициенты, диапазоны и порядок уставок. Если блок повреждён или не поддерживается, он не применяется частично. При неудачной загрузке в начале работы остаются дефолты; при ручном `load` — предыдущие настройки. При ошибке стартовой загрузки в журнал добавляется `EVENT_FAULT` с `CONFIG_ERROR`; отсутствие записи (`-ENOENT`) ошибкой не считается. Событие описывает отклонённую запись: рабочие дефолты исправны, поэтому оно не создаёт активную аварию и не запускает двигатель. Повреждённый блок не перезаписывается автоматически. В `status` видны `settings_ready`, `settings_present` и `settings_error`.

Запуск через `west build -t run` использует файл в каталоге сборки. Для проверки сохранения завершите QEMU через `Ctrl+A`, `X` и запустите снова из того же каталога. Очистка каталога сборки (`build.py -c`) удалит и этот файл — это не перезапуск контроллера с сохранённой flash.

Semihosting нужен только для QEMU. На плате нужно заменить узел файловой flash в overlay разделом настоящей flash и включить Settings/NVS для этой платы. Формат записи и код сохранения остаются теми же.

```bash

git -C ../zephyr-workspace/zephyr fetch --depth 1 origin 6848730b4b3f4d6e9151a0a8873955878be1a18d
```

## Запуск

```bash
python3 build.py -c -r
```

Скрипт очистит каталог сборки, соберёт приложение для `qemu_cortex_m3` и запустит QEMU. Можно сделать то же самое через West:

```bash
west build -b qemu_cortex_m3 -d build .
west build -d build -t run
```

Выход из QEMU: `Ctrl+A`, затем `X`.

## Проверка обрыва вручную

В консоли появится `uart:~$`. Сначала проверяем состояние и запускаем привод:

```text
status
start
status
```

Теперь включаем обрыв. Перед следующим `status` дайте контроллеру один цикл опроса — примерно 100 мс.

```text
inject wire-break on
status
events
```

В статусе должны быть `state=FAULT`, `active=0x1`, `latched=0x1`, ток `current_ua=2000` и выход `output_x100=0`. В журнале появится событие `FAULT` с причиной `faults=0x1`.

Попробуйте сбросить аварию до восстановления датчика:

```text
reset
```

Команда будет отклонена. Убираем обрыв:

```text
inject wire-break off
status
```

После следующего опроса `active` станет `0x0`, но состояние останется `FAULT`, а `latched` — `0x1`. Теперь можно выполнить сброс:

```text
reset
status
```

Контроллер вернётся в `READY`. Выход останется нулевым, пока снова не введём `start`.

Для смены профиля или типа входа:

```text
stop
set profile ahu
set mode 0-10v
status
```

### Журнал

Команда `events` показывает последние 32 события: номер, время от загрузки, состояние, причину аварии, ток, напряжение, обработанное измерение и задание частоты. Записи идут от старых к новым. Когда журнал заполняется, новые события вытесняют старые. Всё хранится в RAM, поэтому после перезапуска журнал пустой.

## Тесты

Для исходников приложения включены `-Wall -Wextra`. Тесты отдельно проверяют повторный отказ пуска без утечки мьютекса, десять тактов насыщения PI и пуск после долгого простоя.

```bash
python "$ZEPHYR_BASE/scripts/twister" -T tests -p qemu_cortex_m3 -O twister-out -j 4
python scripts/demo_test.py --elf build/zephyr/zephyr.elf
```

Через Twister запускаются тесты масштабирования, фильтра, границ входного сигнала, состояний, ограничения частоты и журнала. Отдельный системный тест проходит весь аварийный сценарий с периодическим опросом датчика и проверкой выхода. Он проверяет, что останов происходит не позднее 150 мс после инъекции. Это результат для QEMU; на плате время реакции нужно будет измерить заново.

`demo_test.py` запускает собранное приложение в QEMU и вводит команды через UART, как при ручной проверке выше. Он также проверяет журнал и убеждается, что сброс не запускает привод. Протокол остаётся в `build/demo-test.log`.

Отдельные тесты проверяют единичный выход тока или напряжения за границу при уже заполненном фильтре. Даже с задержками технологических защит в 60 секунд команда приводу должна стать нулевой после первого аварийного отсчёта; нормальный следующий отсчёт не должен сам снять зафиксированную аварию.

Те же проверки выполняются в GitHub Actions. Логи и результаты можно скачать из артефакта `qemu-test-results`.

## YAML-сценарии

Сценарии находятся в `scenarios/controller.yaml`. Это команды Shell и ожидаемые результаты, которые выполняются на собранном приложении в QEMU:

```bash
python -m scripts.run_scenarios --elf build/zephyr/zephyr.elf
python -m scripts.run_scenarios --elf build/zephyr/zephyr.elf --scenario nvs_restart_and_erase
python -m scripts.test_storage --elf build/zephyr/zephyr.elf
python -m unittest discover -s tests/host -p 'test_*.py'
```

Минимальный пример:

```yaml
version: 1
scenarios:
  - name: current_overrange
    steps:
      - command: start
        expect: [OK]
      - command: inject signal 25000
        expect: [OK]
      - status: {state: FAULT, active: 2, latched: 2, output_x100: 0}
      - command: reset
        expect: ["Команда отклонена: -16"]
```

Здесь 25 мА — выход за диапазон (`INPUT_RANGE`, код `0x2`). Для обрыва (`WIRE_BREAK`, `0x1`) используется 2 мА. Проверки не смешивают эти причины.

`status` отдельно показывает `sensor_faults` (обрыв и диапазон входа) и `process_faults` (технологические защиты). Поле `active` — их побитовое объединение. Общая фиксация `latched` и ручной сброс остаются прежними.

Сценарий `nvs_corrupted_crc_restores_defaults` сохраняет изменённые настройки и выполняет `corrupt_settings_crc: true`. Этот шаг останавливает QEMU, портит CRC приложения в изолированном файле flash, пересчитывает внешнюю CRC NVS и запускает QEMU снова. Сценарий проверяет дефолтный профиль, вход, PI и защиту, нулевой выход и ошибку `-EBADMSG`. Для шага нужна ровно одна сохранённая запись поддерживаемой версии; неоднозначный образ считается ошибкой теста.

Шаг `status` ждёт совпадения полей, по умолчанию до 2000 мс. Значение `timeout_ms` можно задать рядом с `status`. Шаг `wait_ms` добавляет паузу, `restart: true` полностью перезапускает процесс QEMU с той же flash. Для `command` обязателен непустой список ожидаемого текста. Неправильные поля, повторяющиеся ключи YAML, пустые сценарии и неизвестное имя сценария завершают прогон с ошибкой.

Каждый сценарий получает отдельный временный каталог flash. Перезапуски внутри одного сценария используют один файл, а между сценариями настройки не переносятся. Обычный `demo_test.py` тоже запускается с изолированной flash, поэтому тесты не портят сохранённые вручную настройки. Сценарий NVS проверяет восстановление профиля, входа, защит и признака отключения, запрет работы с хранилищем во время пуска, отсутствие автопуска и удаление записи. Дополнительный прогон проверяет недоступную flash и повреждение сохранённого блока.

Протоколы сохраняются в `build/scenarios.log` и `build/storage-test.log`. GitHub Actions выполняет эти проверки и сохраняет протоколы вместе с результатами Twister.

## Что менять при переносе на плату

Логика находится в `src/controller.c`: состояния, ПИ-регулятор, защита и журнал. Для синхронизации этот файл использует мьютекс Zephyr. В `src/controller_app.c` находятся периодический опрос и синхронизация с Shell.

Работа с устройствами вынесена в `include/controller_io.h`. Для QEMU используется `src/io_sim.c`, для аппаратного ввода — `src/io_hw.c`. Пример ADC для nRF52840 DK описан ниже. Реальный выход на привод нужно реализовать под выбранный интерфейс.

Выбор аппаратного ввода выполняется через `CONFIG_USE_HW_IO`. Его функции инъекции возвращают `-ENOTSUP`.

Пока реализованы защиты от обрыва токовой петли и выхода сигнала за допустимый диапазон. Аппаратной STO и проверки на реальном оборудовании здесь ещё нет.


## Аппаратный watchdog

Вариант `mps2/an385` запускает CMSDK watchdog с полным временем до сброса 2000 мс. Для него включены `CONFIG_WATCHDOG` и `CONFIG_APP_WATCHDOG`, устройство выбирается по alias `watchdog0`. Сборка `qemu_cortex_m3` остаётся без WDT: у LM3S6965 в этой конфигурации Zephyr нет доступного драйвера watchdog. Команда `crash_test` в ней возвращает `-ENOTSUP`.

```bash
west build -b mps2/an385 -d build-watchdog .
west build -d build-watchdog -t run
```

После загрузки появляется `Watchdog armed: timeout_ms=2000 reset=SOC`. В Shell выполните `start`, затем `crash_test`. Команда выставляет атомарный флаг; на следующем цикле сам поток `main` засыпает навсегда. Shell продолжает работать, но основной цикл больше не кормит watchdog. Примерно через две секунды SoC перезапускается. Сохранённые настройки загружаются из NVS, выход остаётся выключенным, для работы нужен новый `start`. На реальной плате состояние выхода во время зависания и reset дополнительно определяется схемой и драйвером выхода.

`wdt_feed()` вызывается только потоком `main` после возврата из `controller_app_tick()`: чтение входа, `controller_update()` и запись выхода уже завершены. Активная технологическая авария считается успешно обработанным циклом и не вызывает перезагрузку. В таймере, ISR, Shell и обработчике NMI кормления нет. При ошибке инициализации цикл не запускается; при ошибке кормления поток прекращает работу и ждёт аппаратного сброса.

CMSDK-драйвер в закреплённой версии Zephyr отсчитывает два одинаковых окна: первое вызывает NMI, второе — аппаратный reset. Поэтому для этого драйвера устанавливается окно 1000 мс, чтобы полное время до reset составляло 2000 мс. Callback не задан, обработчик NMI драйвера не перезаряжает счётчик. Для остальных драйверов окно API составляет 2000 мс. `WDT_FLAG_RESET_SOC` включает сброс системы, `wdt_setup(..., 0)` оставляет watchdog работающим во время сна.

Автоматическая проверка:

```bash
python -m scripts.test_watchdog --elf build-watchdog/zephyr/zephyr.elf
```

Тест проверяет нормальную работу дольше тайм-аута, затем дважды вызывает `crash_test`. Он ждёт новое сообщение загрузки в том же процессе QEMU, проверяет время сброса, восстановление NVS, очистку журнала и нулевой выход. Результат сохраняется в `build-watchdog/watchdog-test.log`, проверка включена в Actions.

Для реальной платы включите её WDT в devicetree, назначьте alias `watchdog0` и включите `CONFIG_WATCHDOG=y`, `CONFIG_APP_WATCHDOG=y`. Проверьте доступный диапазон тайм-аутов и особенности выбранного драйвера. API контроллера вызывается из потока; для кормления WDT отдельный поток не нужен.


## Аппаратный вход ADC

`CONFIG_USE_HW_IO=y` выбирает `src/io_hw.c`, иначе собирается `io_sim.c`. Готовый пример — `nrf52840dk/nrf52840`; его board-конфигурация включает аппаратный ввод. QEMU по умолчанию использует симулятор. На DK выход на привод пока не подключён: `controller_io_write()` ничего не включает, `controller_io_output()` возвращает 0. Для управления приводом нужна отдельная реализация выхода под выбранный интерфейс.

```bash
west update hal_nordic
west build -b nrf52840dk/nrf52840 -d build-hw .
```

В `boards/nrf52840dk_nrf52840.overlay` заданы два канала SAADC с разрешением 12 бит:

| Вход | Вывод DK | Внешняя цепь | Пересчёт |
| --- | --- | --- | --- |
| 4–20 мА | AIN0 / P0.02 | Шунт 125 Ом | `current_ua = adc_mv * 1000 / 125` |
| 0–10 В | AIN1 / P0.03 | Делитель: 30 кОм сверху, 10 кОм на землю | `voltage_mv = adc_mv * 4` |

Это пример схемы согласования, не разрешение подавать 10 В прямо на ADC. Для реального входного модуля нужны защита входа, соблюдение допустимого напряжения на выводе и общий опорный потенциал либо развязка. Параметры `current-shunt-ohms` и `voltage-divider-multiplier` должны соответствовать вашей цепи. Точность зависит от шунта, делителя и опоры ADC. Обрыв 4–20 мА определяется по току; на входе 0–10 В нулевое напряжение допустимо, поэтому отличить его от обрыва без дополнительной схемы нельзя.

Вызовы `adc_channel_setup_dt()` и `adc_read()` выполняются в отдельном рабочем потоке. Основной цикл ждёт завершения запроса не более 20 мс; захват замка самого модуля использует `K_NO_WAIT`. Даже если драйвер застрял на внутреннем замке, поток контроллера получает `-ETIMEDOUT`. После тайм-аута запрос и буфер остаются во владении рабочего потока до завершения ADC. Поздний результат отбрасывается; новый запрос не запускается поверх старого. Если драйвер не завершился вообще, последующие чтения возвращают тайм-аут без ожидания. Желательно выделить ADC этому модулю, чтобы другие потребители не мешали опросу. Вызовы API ввода допустимы только из потока; рабочий поток ADC не кормит watchdog.

`controller_io_read()` теперь возвращает код результата. Исправный вход — 0; ошибка ADC, преобразования или диапазона — `-EIO`; превышение времени — `-ETIMEDOUT`; неподдерживаемый режим и команды инъекции на аппаратном backend — `-ENOTSUP`. При выходе физического сигнала за диапазон отсчёт сохраняется для штатных защит. При ошибке получения отсчёта поле `read_error` ненулевое, контроллер немедленно фиксирует `INPUT_IO`, сбрасывает фильтр и останавливает выход. В `status` видны код `read_error` и причина `INPUT_IO`; для возобновления нужны исправный вход, `reset` и отдельный `start`.

Twister запускает `tests/io_hw` с драйвером ADC Emulator, но с настоящим `io_hw.c`: проверяются единицы, диапазоны, насыщение ADC, ошибка драйвера, задержанное завершение и восстановление после тайм-аута. В Actions дополнительно проверяется сборка DK. Измерения и электрику на самой плате эти тесты не заменяют.


## Modbus RTU

Используется штатная подсистема Zephyr (`zephyr/modbus/modbus.h`). В сборке `qemu_cortex_m3` сервер включён на UART1, Shell остаётся на UART0. Параметры: адрес устройства **1**, **19200 бод, 8N2**. Modbus обрабатывает запросы в отдельной очереди Zephyr. Чтение обращается к `controller_app_status()`, который берёт замок приложения и мьютекс контроллера. Запись уставки берёт те же замки в том же порядке.

Адреса в таблице — нулевые адреса протокола. В SCADA, использующей обозначения 40001, регистр 0 соответствует 40001.

| Адрес | Значение | Доступ |
| --- | --- | --- |
| 0 | Состояние: STOPPED=0, READY=1, RUNNING=2, FAULT=3 | FC03 |
| 1 | Активные аварии, общая битовая маска | FC03 |
| 2 | Активные предупреждения, битовая маска | FC03 |
| 3 | Измеренное значение, x10 | FC03 |
| 4 | Уставка, x10 | FC03 / FC06 / FC16 |
| 10 | Номинальное напряжение, В | FC03 / FC16 |
| 11 | Номинальный ток, мА | FC03 / FC16 |
| 12 | Номинальная частота, 0,01 Гц | FC03 / FC16 |
| 13 | Номинальная скорость, об/мин | FC03 / FC16 |
| 14 | Число пар полюсов | FC03 / FC16 |

Регистры 3 и 4 — знаковые 16-битные значения в дополнительном коде. Например, −5.0 °C передаётся как −50 (`0xFFCE`). Байты регистра идут старшим вперёд; CRC RTU — младшим вперёд. Уставка проверяется по профилю: pump — 0…1000 (0…100 %), ahu — −200…400 (−20…40 °C). Запись разрешена во время работы, но не меняет состояние и не снимает аварии. Она сохраняется между опросами, сбрасывается при смене профиля, успешном `config load` и перезагрузке; в NVS уставка не записывается.

FC06 возвращает эхо записи. Неизвестные адреса и запись в регистры 0–3 отклоняются. В закреплённой версии Zephyr отказ callback записи, включая недопустимую уставку, преобразуется в исключение `02` (Illegal Data Address). Неверная CRC и чужой адрес игнорируются, broadcast-запись применяется без ответа. FC16 обрабатывается целиком: сначала распаковка и проверка всех адресов, затем проверка текущего профиля и состояния под мьютексом и единая запись. Записываемые блоки — уставка (4) и параметры двигателя (10–14). Адреса 5–9 не определены; запрос через этот разрыв отклоняется целиком. Запрос регистров 4–5 возвращает исключение 02, не меняя уставку. Неправильный формат PDU возвращает 03. FC06 по-прежнему разрешает только уставку в регистре 4; параметры двигателя записываются через FC16.

Команда `modbus_status` выводит готовность интерфейса и оба блока регистров. FC03 создаёт локальный `struct modbus_snapshot` один раз на запрос: `controller_app_status()` копирует все поля под мьютексом, после чего весь ответ формируется только из этой копии. Состояние, аварии и измерение в одном ответе относятся к одному моменту.

В закреплённой версии Zephyr штатные FC03/FC16 имеют callback отдельного регистра. `cmake/modbus_frame_handlers.cmake` собирает копию `modbus_server.c`, где эти две функции маршрутизируются через публичный API custom FC к обработчикам приложения. UART, CRC, broadcast и кодирование исключений остаются в Zephyr. Исходники Zephyr не меняются. `scripts/prepare_modbus_server.py` проверяет SHA-256 исходного сервера и останавливает сборку при несовпадении: обновление Zephyr требует явной проверки адаптера.

Регрессионный сценарий `scenarios/modbus_atomic_write.yaml` отправляет ошибочные FC16, проверяет исключение 02 и читает FC03, подтверждая неизменную уставку. Затем проверяет допустимую запись. Шаг YAML `modbus_write_multiple` содержит `address`, `values` (uint16) и `expect_exception` (0 означает успешное подтверждение). Лог — `build/modbus-atomic.log`; сценарий включён в Actions. Ztest дополнительно проверяет снимки FC03 во время параллельных переходов RUNNING/FAULT.

```bash
python -m scripts.run_scenarios --file scenarios/modbus_atomic_write.yaml \
  --elf build/zephyr/zephyr.elf --log build/modbus-atomic.log
```

Проверка протокола в QEMU:

```bash
python -m scripts.test_modbus --elf build/zephyr/zephyr.elf
```

Тест подключается ко второму UART через изолированный UNIX-сокет, передаёт настоящие RTU-кадры и параллельно использует Shell. Проверяет FC03/FC06, отрицательную уставку, сохранение между тактами, аварии, исключения, неверную CRC, адрес устройства и broadcast. Протокол — `build/modbus-test.log`. В devicetree UART1 QEMU выбран PL011-драйвер: модель поддерживает его регистры и настройку формата линии, необходимую подсистеме Modbus.

Для nRF52840 DK есть дополнительный overlay: TX — P1.01, RX — P1.02. Он добавляется к overlay аппаратного ADC:

```bash
west build -b nrf52840dk/nrf52840 -d build-hw-modbus . -- \
  -DEXTRA_CONF_FILE=config/modbus.conf \
  -DEXTRA_DTC_OVERLAY_FILE=boards/nrf52840dk_modbus.overlay
```

Это UART уровня MCU, не физический RS-485. Для RS-485 нужен трансивер; `de-gpios` и `re-gpios` задаются в узле `controller_modbus` под вашу схему. На другой плате включите отдельный UART с поддержкой настройки формата линии, задайте такой же дочерний узел и подключите `config/modbus.conf`. Сборки DK проверяются в CI; обмен на физической плате ещё не проверялся.


## Диагностика аварий и очистка журнала

`status` показывает состояние, `sensor_faults` с расшифровкой `sensor_fault_names`, `process_faults` с `process_fault_names` и зафиксированные причины `latched` / `latched_names`. Имена соответствуют существующим защитам: `WIRE_BREAK` — обрыв токовой петли, `INPUT_RANGE` — диапазон входа, `INPUT_IO` — ошибка получения отсчёта, `PROCESS_LOW` / `PROCESS_HIGH` — нижняя и верхняя технологические защиты. Единицы процесса зависят от профиля; отдельных защит тока или напряжения привода сейчас нет.

`faults clear_history` очищает весь кольцевой журнал событий под мьютексом контроллера. Повторная очистка допустима. Нумерация следующих записей продолжается; активные и зафиксированные аварии, предупреждения, состояние и выход сохраняются. Для снятия аварии после устранения причины по-прежнему нужен `reset`.


### YAML-проверка Modbus

`scenarios/modbus_read_state.yaml` ждёт READY и читает пять Holding Registers через FC03. Ожидаемый ответ: `[1, 0, 0, 500, 500]`. Затем сценарий вводит обрыв через Shell, ждёт FAULT и тем же запросом проверяет `[3, 1, 0, 0, 500]`: состояние FAULT, маска WIRE_BREAK=1, предупреждений нет, измерение недостоверно, уставка сохранена.

```bash
python -m scripts.run_scenarios --file scenarios/modbus_read_state.yaml \
  --elf build/zephyr/zephyr.elf --log build/modbus-scenario.log
```

Шаг `modbus_read` задаёт `address`, `count` и точный список `expect` из значений uint16. Runner подключает UART1 QEMU через временный UNIX-сокет и отправляет реальные RTU-кадры адресу 1; UART0 используется для Shell. Проверяются CRC, код функции, длина ответа и значения регистров. Запрос пяти регистров с адреса 0: `01 03 00 00 00 05 85 C9`. TX/RX попадают в лог. При `restart` сокет закрывается и подключается заново. Дополнительные Python-библиотеки не нужны. Сценарий включён в Actions.


## Concurrency and Threading Model

У приложения четыре основных контекста выполнения. Набор потоков зависит от сборки: ADC worker включается с `CONFIG_USE_HW_IO`, очередь Modbus — с `CONFIG_APP_MODBUS` и `CONFIG_MODBUS_WORKQUEUE`. В QEMU LM3S используется симулятор и Modbus; в варианте MPS2 проверяется watchdog; на DK доступен аппаратный ADC с опциональным Modbus. ISR не вызывает API контроллера с мьютексами.

```text
Main
  controller_app_tick()
    controller_lock -> controller.mutex
    controller_io_read() -------- запрос ------> ADC Worker
                      <--- adc_finished -------- adc_read()
          ожидание до 20 мс
    controller_update()
    controller_io_write()
    освободить замки
  wdt_feed()                     только если включён APP_WATCHDOG
  k_sleep(100 мс)

Modbus workqueue                 отдельный поток обработки запросов
  UART RX / сборка RTU -> callback регистра
    controller_app_status() -> controller_lock -> controller.mutex
    копирование состояния -> освободить замки -> ответ Zephyr Modbus
  запись уставки -> controller_app_setpoint_set() -> те же замки

Shell
  status / events -> копирование под замками -> вывод
  start / stop / reset / configure / faults clear_history -> API под замками
```

**Main.** Периодический расчёт, чтение входа и запись выхода выполняются в одном потоке. Watchdog кормится только после возврата из всего `controller_app_tick()`. Если цикл завис, кормления не будет. Авария датчика считается обработанным результатом: контроллер фиксирует причину и выключает выход, продолжая обслуживать диагностику. Пауза 100 мс не задаёт жёсткий период: к ней добавляется время работы; PI использует фактический `dt`. Shell также может вызвать внеочередное чтение и `controller_update()` перед пуском или сбросом, под теми же замками; watchdog из Shell не кормится.

**ADC Worker.** Только этот поток выполняет блокирующие вызовы драйвера ADC. Запрос и результат передаются через общую структуру и семафоры `adc_request` / `adc_finished`. `adc_lock` защищает отправителя; буфер нельзя менять, пока рабочий поток не закончил запрос. При тайм-ауте основной цикл получает `-ETIMEDOUT`, а поздний отсчёт отбрасывается. Рабочий поток не захватывает мьютекс контроллера и не кормит watchdog.

**Modbus.** UART обслуживает транспорт, callback регистров выполняется в очереди Modbus. Код читает локальную копию после захвата `controller.mutex` внутри `controller_app_status()`. FC03 получает один локальный снимок на весь запрос и формирует весь ответ из него. FC16 сначала проверяет пакет, затем под мьютексом повторно проверяет актуальный профиль и применяет запись целиком. Регистры в PDU кодируются через `sys_put_be16()`, транспорт и CRC обслуживает Zephyr.

**Порядок замков.** В приложении сначала берётся `controller_lock`, затем `controller.mutex`. Внутри операции могут браться `adc_lock` или замок хранилища Settings; обратного захвата нет. Публичные функции ядра повторно берут `controller.mutex` — Zephyr допускает рекурсивный захват своим потоком. Вывод Shell выполняется после получения копии данных. Очистка журнала, изменение уставки и переконфигурация используют тот же порядок, что и основной цикл.

## Паспортные параметры двигателя

`controller_config.motor` содержит `struct motor_parameters`. В `controller_init()` задаётся пример для двигателя 5,5 кВт: `nominal_voltage_v=400`, `nominal_current_ma=11500`, `nominal_frequency_x100=5000`, `nominal_speed_rpm=1450`, `pole_pairs=2`. Значения выводятся в `status`. Расчёт PI и верхняя граница задания частоты остаются прежними. Из номинального тока и частоты рассчитываются отдельные моторные защиты; Modbus предоставляет паспортные поля в регистрах 10–14.

NVS сохраняет паспорт и тип двигателя в записи версии 3 (124 байта). Записи v1 (100 байт) и v2 (120 байт) продолжают читаться: в v1 паспорт заполняется дефолтами, отсутствующий тип в обеих версиях становится `induction`. Следующее сохранение записывает v3; автоматической перезаписи при загрузке нет. Расчётные данные пересчитываются, отдельно во flash не дублируются.


### Настройка двигателя через Modbus

Чтение блока FC03 с адреса 10 и количеством 5 возвращает по умолчанию `[400, 11500, 5000, 1450, 2]`. Допустимы полная запись FC16 или запись части блока. Каждый параметр — положительный uint16, без знакового преобразования. Частота хранится в сотых долях герца: 5000 означает 50 Гц.

Перед коммитом проверяется весь итоговый набор, включая неизменяемые запросом поля. Для номинальной скорости требуется `rpm * pole_pairs * 100 <= frequency_x100 * 60`; проверка выполняется в `int64_t`. То есть скорость не должна превышать синхронную скорость поля. Это проверка согласованности демо, а не полная модель двигателя или копия правил ACS880. Мощность, КПД, cos φ и электрическая схема подключения пока не задаются.

Паспорт изменяется только в STOPPED/READY; в RUNNING/FAULT FC16 возвращает исключение 02. При любой ошибке весь пакет остаётся неприменённым. Частичная запись строит кандидата из актуальных параметров под мьютексом, затем после проверки заменяет структуру целиком — без потери параллельных изменений. FC03 считывает всю структуру двигателя в один снимок. Проверки выполняются также при обычной конфигурации и загрузке NVS, поэтому обхода через сохранённую запись нет.

При FC16 невалидные значения параметров двигателя возвращают исключение `03` (Illegal Data Value). Проверка включает расчёт пар полюсов: частота 1–500 Гц, скорость 50–30000 об/мин, результат 1–100 пар. При отказе конфигурация не изменяется. Эти же проверки действуют при конфигурации через Shell и загрузке NVS. Запрещённое состояние и неверный адрес по-прежнему возвращают `02`.

Рабочие параметры двигателя проверяются также в каждом `controller_update` перед PI-расчётом. Если они повреждены, возникает `CONFIG_ERROR` (`0x0100`, в текущей карте входит в `process_faults`): выход и интегратор обнуляются, причина фиксируется в `latched_faults` и журнале. Пока причина активна, сброс запрещён. После устранения причины нужны отдельные сброс и пуск. Расчётные данные хранятся отдельно в `controller.motor`: `pole_pairs_calc`, `sync_speed_rpm` и `slip_x1000` (промилле). Они пересчитываются при инициализации, конфигурации, записи паспорта через Shell/Modbus и загрузке NVS; отдельно во flash не сохраняются. Синхронная скорость равна `60 * nominal_frequency_x100 / (pole_pairs_calc * 100)`, скольжение — `(sync_speed_rpm - nominal_speed_rpm) * 1000 / sync_speed_rpm`. Допустимое скольжение 0–200 промилле; невалидный кандидат отклоняется целиком. Для штатного двигателя получаются 1500 об/мин и 33 промилле. Формула компенсации и её ограничения описаны ниже.


Прежний блок Modbus 10–14 меняет только RAM; для его сохранения нужен `config save` в Shell. Новый блок 40–43 автоматически сохраняется в NVS. Пример: отдельная запись 40 Гц при текущих 1450 об/мин и двух парах полюсов отклоняется. Совместная запись частоты 4000 и скорости 1150 в регистры 12–13 проходит.

```bash
python -m scripts.run_scenarios --file scenarios/modbus_motor_parameters.yaml \
  --elf build/zephyr/zephyr.elf --log build/modbus-motor.log
```

Сценарий проверяет дефолты, отказы без частичной записи, согласованную пакетную запись, запрет изменения работающего и аварийного контроллера, сохранение и восстановление NVS. Ztest проверяет также снимок FC03 при параллельной смене двух наборов параметров.


### Загрузка паспорта двигателя при старте

`controller_init()` задаёт дефолты и инициализирует мьютекс. Сразу после неё `main` вызывает `controller_app_settings_init()` для чтения NVS. Зависимость от flash остаётся в слое приложения.

В записи v3 сохраняются все паспортные поля: тип, номинальные напряжение, ток, частота, обороты и число пар полюсов. Вычисляемые `pole_pairs_calc`, `sync_speed_rpm`, `slip_x1000` не сериализуются. `max_freq_hz_x100` тоже вычисляемый и read-only: он всегда равен 120% номинальной частоты, поэтому после загрузки пересчитывается, а не читается как отдельная уставка.

Декодер проверяет длину, версию, CRC и весь кандидат до применения. Успешная загрузка проходит через `controller_parameters_apply` и `controller_configure`: после `calculate_pole_pairs` вызывается `calculate_sync_speed_and_slip`. При несовместимых значениях, например скольжении выше 200 промилле, кандидат отклоняется целиком. На старте в RAM остаются дефолтные 400 В, 11,5 А, 50 Гц, 1450 об/мин и `induction`, расчётные значения — 2 пары, 1500 об/мин, 33 промилле и предел 6000. В журнал записывается `EVENT_FAULT` с `FAULT_CONFIG_ERROR`, а `settings_error` содержит причину отказа. Пуск по-прежнему выполняется только отдельной командой.

При ручном `config load` ошибка оставляет текущую конфигурацию, а не возвращает её к заводской. Это позволяет не потерять действующие настройки при неудачной попытке загрузки.

## Modbus motor_data: регистры 40–49

Адреса ниже — смещения holding registers от нуля. FC03 читает до восьми регистров 40–47 одним атомарным снимком паспорта и расчётных данных, с кодированием big-endian. Регистры 48–49 зарезервированы: чтение и запись возвращают Exception 02.

| Регистр | Поле | Единицы и диапазон | Доступ |
| --- | --- | --- | --- |
| 40 | type | 0 induction, 1 pmsm, 2 synrm | FC03/FC16 |
| 41 | nominal_frequency_x100 | 100–50000, сотые герца | FC03/FC16 |
| 42 | nominal_speed_rpm | 50–30000 об/мин, uint16 | FC03/FC16 |
| 43 | nominal_current_ma / 100 | 1–6400, шаг 100 мА, до 640 А | FC03/FC16 |
| 44 | pole_pairs_calc | 1–100 пар | FC03 |
| 45 | sync_speed_rpm | об/мин | FC03 |
| 46 | slip_x1000 | 0–200 промилле | FC03 |
| 47 | max_freq_hz_x100 | 120% номинала, сотые герца | FC03 |

Дефолтное чтение 40–47 возвращает `[0, 5000, 1450, 115, 2, 1500, 33, 6000]`. Значение 115 в регистре 43 соответствует 11500 мА (11,5 А). При чтении тока дробная часть после деления на 100 отбрасывается; FC16 записывает точное кратное 100 мА.

FC16 может менять любой непрерывный подблок 40–43. Например, `[1, 6000, 1750, 150]` с адреса 40 задаёт PMSM, 60 Гц, 1750 об/мин и 15 А. При записи частоты или оборотов паспортное число пар полюсов автоматически согласуется с `calculate_pole_pairs`; весь кандидат проверяется, включая синхронную скорость и скольжение.

Обработчик сначала распаковывает значения во временный массив. Затем приложение под замком приложения и мьютексом контроллера строит и валидирует кандидат, сохраняет его в NVS и применяет одной операцией. Ошибка расчёта, невалидный параметр или отказ NVS возвращают Exception 04 без изменения RAM и журнала. Запись в RUNNING/FAULT также возвращает 04. Успешная FC16 сохраняет весь текущий набор параметров; дополнительный `config save` не нужен. Перезапуск восстанавливает паспорт и пересчитывает производные поля.

Попытка записи 44–47 или пересечения границы, например запрос 43–44, возвращает Exception 02 целиком: ток в регистре 43 не меняется. Неправильный формат PDU возвращает 03. FC06 для нового блока запрещён. Новое правило Exception 04 относится к блоку 40–43; коды ошибок прежних регистров не меняются.

Полный номинальный ток в паспорте теперь допускается до 640000 мА. Старый регистр 11 имеет единицу 1 мА и не вмещает ток выше 65535 мА: при чтении он насыщается значением 65535, не переполняется. Для больших токов нужно читать регистр 43. Прежний FC16-блок 10–14 остаётся доступен и не выполняет автосохранение.

```bash
python -m scripts.run_scenarios --file scenarios/modbus_motor_data.yaml \
  --elf build/zephyr/zephyr.elf --log build/modbus-motor-data.log
```

Сценарий проверяет запись, отказ с 04 без частичного применения, read-only границу, 640 А, запрет записи в RUNNING/FAULT и перезапуск без `config save`. Ztest дополнительно проверяет отказ NVS, big-endian и согласованность всех восьми полей FC03 при параллельной смене паспорта.

## Компенсация скольжения (slip compensation)

Компенсация работает только в RUNNING и использует фактический ток двигателя из `sample.motor.current_ma`. Ток входного датчика 4–20 мА в этом расчёте не участвует.

```text
load_x1000 = actual_current_ma * 1000 / nominal_current_ma
slip_comp_x100 = slip_x1000 * nominal_frequency_x100 * load_x1000 / 1000000
```

Частота хранится в сотых герца, нагрузка и скольжение — в промилле. При `slip_x1000 = 33`, номинале 50 Гц (`5000`) и токе 100% (`load_x1000 = 1000`) добавка равна `33 * 5000 * 1000 / 1000000 = 165`, то есть 1,65 Гц. При 30% нагрузки добавка равна 49 (0,49 Гц), при нулевом токе — нулю. Дробная часть отбрасывается.

Добавка ограничена диапазоном 0–500 (0–5 Гц). Она прибавляется к PI-выходу до anti-windup и верхнего ограничения: итоговая команда остаётся в диапазоне 0–5000 (0–50 Гц), скорость изменения — не более 100 (1 Гц) за тик. При нулевом скольжении или невалидной обратной связи добавки нет; потеря уже доступной обратной связи обрабатывается защитой двигателя. Невалидный паспорт отклоняется общей проверкой конфигурации.

Промежуточные вычисления выполняются в `int64_t`. Насыщение проверяется до тройного произведения, чтобы завышенный ток не вызвал переполнение. Тест `test_slip_compensation` сравнивает установившийся выход двух контроллеров: разница при полной нагрузке — 165, после снятия нагрузки — 0. Дополнительные тесты проверяют предел 5 Гц, anti-windup и останов.

Это линейная оценка по току, а не полная модель асинхронного двигателя. Подробности — в [допущениях](docs/ASSUMPTIONS.md).

## Превышение частоты (overfrequency)

Пороги вычисляются из номинала двигателя в `int64_t` с целочисленным делением:

```text
of_warn_x100 = nominal_frequency_x100 * 105 / 100
of_trip_x100 = nominal_frequency_x100 * 110 / 100
```

В RUNNING фактическая частота строго выше 105% вызывает предупреждение, строго выше 110% — аварию без задержки. При аварии предупреждение также остаётся активным. На самой границе новая защита не срабатывает. Для 50 Гц предупреждение начинается выше 52,50 Гц, авария — выше 55,00 Гц: 53 Гц дают предупреждение без останова, 56 Гц останавливают контроллер.

Используются общие маски: `WARNING_MOTOR_FREQUENCY = 0x08` в предупреждениях и `FAULT_MOTOR_OVERFREQUENCY = 0x40` в авариях. Они доступны в Shell и регистрах Modbus 2 и 1 соответственно. Бит `0x08` общей маски аварий занят `FAULT_PROCESS_HIGH`, поэтому для превышения частоты он не переиспользуется.

Авария записывается в журнал и `latched_faults`, выход обнуляется. `reset` возвращает `-EBUSY`, пока причина активна. Гистерезис равен 2% номинала: при 50 Гц активная авария снимается на 54 Гц и ниже, предупреждение — на 51,50 Гц и ниже. Активная причина проверяется и в FAULT; исчезновение причины не сбрасывает защёлку и не запускает двигатель. Нужны отдельные `reset` и `start`. Новое превышение в STOPPED/READY не взводит частотную защиту.

`test_overfrequency_trip` проверяет 56 Гц, останов, защёлку и отказ сброса. `test_overfrequency_warning` проверяет 53 Гц, отсутствие аварии и единственную запись `EVENT_WARNING` без дублей на следующих тиках. YAML-сценарий `motor_frequency_trip_uses_updated_nvs_rating` проверяет пересчёт порогов после сохранения и загрузки паспорта.

## Моторные защиты: ток и фактическая частота

Сигнал процесса и обратная связь двигателя разделены. `current_ua` — ток аналогового входа 4–20 мА, `measured_x10` — проценты насоса или температура приточки. Моторные защиты получают отдельные `sample.motor.current_ma` и `sample.motor.frequency_x100`; технологические пороги 10/90% или температурные пределы сохраняются.

`protection_defaults()` формирует оба набора. Моторные пороги рассчитываются из `config.motor`: предупреждение — 105% номинала, авария — 110%. Для тока сохраняются задержки 500/1000 мс и сравнение `>=`. По фактической частоте превышение фиксируется только в RUNNING, строго при `>` и без задержки; активная причина проверяется и после останова. Авария по частоте защёлкивается до устранения причины и ручного сброса. Гистерезис — 2% номинала, снятие происходит на границе «порог − гистерезис». Пороги частоты вычисляются целочисленным делением с округлением вниз; пороги тока и гистерезис округляются вверх. Вычисления идут в `int64_t`, результат хранится в `int`, поэтому порог 110% может превышать 65535 без переполнения. Это простые пороговые защиты демо, не тепловая модель или I²t-защита ACS880.

| Канал | Номинал | Предупреждение | Авария | Гистерезис |
| --- | --- | --- | --- | --- |
| Ток | 11500 мА | 12075 мА | 12650 мА | 230 мА |
| Фактическая частота | 5000 (50 Гц) | 5250 (52,50 Гц) | 5500 (55 Гц) | 100 (1 Гц) |

Пороги пересчитываются при инициализации, изменении моторного паспорта через FC16 и загрузке NVS. В NVS сохраняется паспорт, а не дублирующие производные пороги. При перенастройке прерываются старые таймеры моторных защит; технологические настройки не изменяются. `protect show` выводит производные пределы с единицами, гистерезисом и задержками; через `protect set` они не меняются.

В симуляторе исправная обратная связь доступна сразу: фактическая частота следует последней команде выхода, ток при работе равен 50% номинального, при останове — нулю. Это тестовый источник, а не электромеханическая модель. Инъекции независимы от входа процесса:

```text
inject motor-current 12075
inject motor-current 12650
inject motor-current off
inject motor-frequency 5500
inject motor-frequency off
```

Предупреждение сохраняет работу; авария обнуляет выход и фиксируется до восстановления обратной связи, `reset` и отдельного `start`. Защиты проверяются также в READY и FAULT. Моторные аварии входят в `process_faults`, ошибка обратной связи — в `sensor_faults`; объединение доступно в прежнем регистре Modbus 1, предупреждения — в регистре 2.

| Причина | Маска |
| --- | --- |
| Предупреждение MOTOR_CURRENT | warnings=0x04 |
| Предупреждение MOTOR_FREQUENCY | warnings=0x08 |
| MOTOR_OVERCURRENT | faults=0x20 |
| MOTOR_OVERFREQUENCY | faults=0x40 |
| MOTOR_FEEDBACK | faults=0x80 |

`status` показывает `motor_actual_current_ma` и `motor_actual_frequency_x100` отдельно от паспортных `motor_current_ma` и `motor_frequency_x100`, а также доступность и валидность обратной связи. Журнал хранит фактические значения и номиналы на момент события. После появления доступной обратной связи её потеря или невалидный отсчёт вызывает MOTOR_FEEDBACK, не снимая уже активные защиты. Неисправные отсчёты не засчитываются в задержки.

В `io_hw.c` моторный канал пока не реализован: `available=false`, значения −1, инъекции возвращают `-ENOTSUP`. До первого доступного моторного отсчёта моторные защиты не активируются; это явно отличается от отказа подключённого канала. Физический выход по-прежнему отключён. Перед подключением реального привода нужно реализовать измерение моторного тока и частоты и обеспечить обязательную доступность этой обратной связи.

```bash
python -m scripts.run_scenarios --file scenarios/motor_protections.yaml \
  --elf build/zephyr/zephyr.elf --log build/motor-protections.log
```

Сценарии проверяют предупреждение, останов с фиксацией причины, ручное восстановление и пересчёт частотных порогов после изменения паспорта и перезапуска NVS. Ztest дополнительно проверяет гистерезис, краткие пики, совместные аварии и потерю обратной связи.


## Stall protection: перегрузка на низкой частоте

Отдельная защита `MOTOR_STALL` проверяет фактическую обратную связь двигателя. Условие: `current_ma > 2 * nominal_current_ma` **и** `frequency_x100 < 500` непрерывно дольше 500 мс. Новая выдержка запускается только в RUNNING. Границы строгие: ровно 200%, ровно 5 Гц или ровно 500 мс ещё не вызывают stall. При периоде опроса 100 мс останов происходит на первом тике после превышения выдержки.

По умолчанию номинал равен 11500 мА: ток 23001 мА при 4,99 Гц запускает отсчёт, а 23000 мА или 5,00 Гц — нет. Выход из любого условия, останов или повторный пуск сбрасывают незавершённый отсчёт. Короткие эпизоды не суммируются. Потеря измерений прерывает выдержку; если stall уже активен, потеря обратной связи не снимает его.

Авария `FAULT_MOTOR_STALL = 0x0200` входит в `process_faults`, `active_faults`, `latched_faults` и регистр Modbus 1. Контроллер переходит в FAULT, обнуляет выход и интегратор, журнал получает `EVENT_FAULT` с именем `MOTOR_STALL`. Повторные тики с той же причиной не дублируют событие. `reset` запрещён, пока условие активно. После устранения причины защёлка остаётся до ручного сброса; пуск — отдельной командой.

`status` показывает `motor_stall_current_ma`, `motor_stall_frequency_x100`, `motor_stall_time_ms` и `motor_stall_pending`. Пороги 200%, 5 Гц и 500 мс пока фиксированы в коде, не являются изменяемыми настройками NVS. Отсчёт и состояние защиты не сохраняются при перезапуске.

Overcurrent и overfrequency продолжают работать независимо. У overcurrent в демо сохраняется задержка 1000 мс: stall при указанных условиях может отключить выход раньше. Если повышенный ток сохранится после останова, overcurrent тоже может добавиться к маске аварий. Stall не заменяет тепловую модель или контроль оборотов ротора.

```text
start
inject motor-frequency 400
inject motor-current 23001
status
reset
inject motor-current 0
reset
inject motor-current off
inject motor-frequency off
start
```

Первый `reset` при активной причине будет отклонён. После `inject motor-current 0` дождитесь следующего опроса и исчезновения активной причины перед сбросом.

Сценарий `tests/conformance/scenarios/motor_stall.yaml` проверяет инъекции, останов, журнал, Modbus, защёлку и отдельный пуск; он включён в CI. Ztest проверяет границы, непрерывность выдержки, stop/start, потерю обратной связи и откат времени.

## Команда motor в Shell

`motor status` берёт один снимок под мьютексом и выводит тип, режим PI, паспорт, расчётные пары полюсов, синхронную скорость, скольжение и предел частоты. Для дефолтов: `type=induction mode=PI`, `pole_pairs_calc=2`, `sync_speed_rpm=1500`, `slip_x1000=33`, `max_freq_hz_x100=6000`. Последнее значение — 120% номинала; действующий предел команды равен меньшему из него и общего ограничения демо 5000 (50 Гц), он выводится как `effective_max_freq_hz_x100`.

```text
motor status
motor set freq 60
motor set speed 1750
motor set current 15000
motor set type induction
motor set type pmsm
motor set type synrm
```

`freq` принимает целые герцы и переводит их в сотые герца, `speed` — целые об/мин, `current` — мА. Полные имена `nominal_voltage_v`, `nominal_current_ma`, `nominal_frequency_x100`, `nominal_speed_rpm` и `pole_pairs` остаются доступны; при записи частоты полным именем единицы — сотые герца. Тип — паспортное поле: для PMSM и SynRM пока не реализованы отдельные алгоритмы управления, режим остаётся PI.

Изменение разрешено только в STOPPED/READY. Shell захватывает замок приложения, затем мьютекс контроллера, строит временный кандидат, проверяет частоту, обороты, пары полюсов и скольжение. При невалидном кандидате возвращается `-EINVAL`, при RUNNING/FAULT — `-EBUSY`. Перед применением кандидат сохраняется в NVS вместе с текущим профилем, PI и защитами; при недоступной flash или ошибке записи прежние RAM-параметры, расчётные данные и журнал не меняются. Все проверки и сохранение проходят под теми же замками. Успешный ответ означает сохранение без дополнительного `config save`. Это отличается от FC16: Modbus по-прежнему меняет RAM, сохранение выполняется явно.

После записи пересчитываются `pole_pairs_calc`, `sync_speed_rpm`, `slip_x1000`, `max_freq_hz_x100 = nominal_frequency_x100 * 120 / 100` и моторные пороги. Производные значения после перезапуска восстанавливаются из паспорта, который хранится в NVS v3; v1/v2 читаются совместимо.

При изменении связанных полей порядок имеет значение. Для перехода с 50 Гц / 1450 об/мин на 40 Гц / 1150 об/мин сначала уменьшите `speed` до 1150, затем задайте `freq 40`. Для одновременной смены нескольких полей можно использовать FC16.

```bash
python -m scripts.run_scenarios --file scenarios/motor_shell.yaml \
  --elf build/zephyr/zephyr.elf --log build/motor-shell.log
```

Сценарий проверяет все пять параметров, единицы вывода, ошибочные значения и межпараметрные ограничения, согласованность с Modbus, запрет записи во время работы и аварии, сохранение и восстановление NVS.

## Conformance: проверка паспорта двигателя

`tests/conformance/scenarios/motor_config_valid.yaml` задаёт 50 Гц, 1450 об/мин и 11500 мА через Shell и читает FC03 44–46: ожидаются `[2, 1500, 33]`.

`motor_config_invalid.yaml` проверяет отказ Shell с `-EINVAL` и FC16 с Exception 04 для скольжения 300 промилле: 50 Гц, одна пара, 2100 об/мин дают синхронную скорость 3000 об/мин. После отказа паспорт и расчётные значения остаются прежними; перезапуск подтверждает, что невалидные значения не попали в NVS. Одна паспортная пара задаётся перед проверкой, чтобы кандидат дошёл до проверки скольжения.

100 об/мин при 50 Гц не дают превышения скольжения: расчёт возвращает 30 пар, 100 синхронных об/мин и 0 промилле. Сценарий явно проверяет этот случай как допустимый, затем восстанавливает 1450 об/мин.

```bash
python -m scripts.run_scenarios --file tests/conformance/scenarios/motor_config_valid.yaml \
  --elf build/zephyr/zephyr.elf --log build/motor-config-valid.log
python -m scripts.run_scenarios --file tests/conformance/scenarios/motor_config_invalid.yaml \
  --elf build/zephyr/zephyr.elf --log build/motor-config-invalid.log
```

Оба сценария включены в Actions, UART/RTU-логи сохраняются в артефактах.
