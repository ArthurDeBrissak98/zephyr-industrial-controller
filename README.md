# Контроллер на Zephyr и QEMU

Демонстрационный проект: эмулируем датчик 4–20 мА, управляем заданием частоты и проверяем, как контроллер реагирует на обрыв. Всё запускается в QEMU на `qemu_cortex_m3` — эмуляции ARM Cortex-M3, TI LM3S6965. В дальнейшем хочу перенести ту же логику на реальную плату.

Главный сценарий простой: запускаем привод, подаём обрыв датчика и получаем останов с записью причины в журнал. После восстановления сигнала авария остаётся зафиксированной. Её нужно сбросить вручную, а затем отдельно дать команду пуска.

## Как работает

После загрузки частота равна нулю. Когда приходит первый нормальный отсчёт, контроллер переходит из `STOPPED` в `READY` и ждёт `start`. Во время работы ПИ-регулятор задаёт частоту от 0 до 50 Гц. Шаг ограничен: не больше 1 Гц за цикл.

Датчики опрашиваются раз в 100 мс. Если ток падает ниже 3,6 мА, контроллер переходит в `FAULT` и сразу обнуляет выход. Плавный останов в этом случае не применяется. Команда `stop` не снимает аварию, а `reset` не принимается, пока причина не устранена.

Есть два профиля: насос (`pump`) и приточка (`ahu`). Пока привод остановлен и нет зафиксированной аварии, можно сменить профиль и выбрать вход `4-20ma` или `0-10v`. Для входа напряжения команда имитации обрыва токовой петли отклоняется.

### Время расчёта PI и доступ из потоков

PI учитывает фактическое время между вызовами `controller_update`: ошибка умножается на `dt` в миллисекундах. Последняя временная метка хранится в `last_update_ms`. При инициализации она равна нулю, при успешном пуске, сбросе аварии и переконфигурации устанавливается в `now_ms`. При нулевом или отрицательном `dt` интегратор не меняется. В конце каждого вызова, включая обработку аварии, `last_update_ms` получает переданный `now_ms`. Время остановки не накапливается после нового пуска.

Интегратор хранится в `int64_t`, в единицах «ошибка × мс», с насыщением ±10000000. Проверка насыщения выполняется до умножения, поэтому большой интервал не вызывает переполнение. Коэффициент интегральной части приведён к прежнему периоду 100 мс: при штатном цикле отклик сохраняется. Ограничения выхода прежние — 0–50 Гц и не больше 1 Гц за вызов.

Параметры PI хранятся в `controller_config.pid`: `bias_x100=2500`, `kp=50`, `ki=5`, `divisor=10` по умолчанию. Смещение задаётся в сотых долях Гц. В `controller_configure` коэффициенты проверяются: `kp` и `ki` неотрицательные, делитель положительный, смещение в диапазоне 0–5000. При смене только профиля или входа нужно сохранить текущие `pid` из конфигурации.

У интегратора есть условное накопление: если рассчитанное задание достигает 5000 при положительной ошибке либо 0 при отрицательной, новое значение интеграла не сохраняется. Обратная ошибка позволяет уменьшать накопленный интеграл. Ограничения частоты и шага остаются прежними.

`controller_update` вызывается из потока `main`: после каждого цикла он ждёт 100 мс. Это номинальный период; PI использует фактическое время между вызовами. Команды `start`, `stop`, `reset`, настройка и операции NVS выполняются в потоке Shell. Порядок захвата: замок приложения → мьютекс контроллера → замок хранилища. При переносе на плату драйвер может принимать данные в ISR, но вызывать API контроллера нужно из потока, например через очередь сообщений.

В `struct controller` находится мьютекс Zephyr. Функции изменения состояния и чтения журнала берут его внутри. Приложение держит тот же мьютекс при копировании статуса и обмене с эмулятором, а внешний замок приложения объединяет чтение входа, расчёт и запись выхода в одну операцию. Мьютексы Zephyr допускают повторный захват своим потоком. `controller_init` нужно вызывать до запуска рабочих потоков; повторная инициализация допустима только при отсутствии обращений к контроллеру.

## Обработка датчика

Контроллер получает от входа ток в мкА или напряжение в мВ. По этому значению рассчитывается измерение для регулятора:

| Вход | Насос | Приточка |
|---|---|---|
| 4–20 мА | 0–100% | −20…+40 °C |
| 0–10 В | 0–100% | −20…+40 °C |

Все расчёты целочисленные. В `status` поле `scaled_x10` показывает пересчитанное значение, а `measured_x10` — среднее по четырём последним отсчётам. Оба поля в десятых долях: `500` для насоса — это 50%, `-150` для приточки — −15 °C. На старте усредняются только уже полученные отсчёты, без заполнения окна нулями.

Для токового входа допустим диапазон 3,6–21 мА. Участки 3,6–4 мА и 20–21 мА считаются допустимыми, но при пересчёте ограничиваются нижним и верхним значением шкалы. Ниже 3,6 мА фиксируется обрыв (`0x1`), выше 21 мА — выход за диапазон (`0x2`). Для входа напряжения допустимы только 0–10 В включительно; выход в любую сторону даёт `0x2`.

Проверка диапазона идёт до усреднения: один аварийный отсчёт обнуляет команду приводу в том же такте обработки. Контроллер не ждёт заполнения окна фильтра или задержек технологических защит. Сам отсчёт не попадает в фильтр. После восстановления входа или смены настроек история фильтра очищается. Пока `signal_valid=no`, значения измерения не используются для регулирования.

Показания можно задать вручную через Shell. Например, для входа 4–20 мА:

```text
inject signal 12000
status
inject signal 22000
status
events
inject signal off
reset
```

`12000` — нормальные 12 мА, `22000` — выход за верхнюю границу. После каждой смены сигнала подождите хотя бы один цикл опроса; для установления среднего — четыре. На входе 0–10 В та же команда принимает мВ, например `inject signal 5000`. `off` возвращает обычную модель датчика. Если отдельно включён `inject wire-break on`, он имеет приоритет: сначала отключите его.

### Что видно в диагностике

В `status` остаются числовые маски `active`, `latched` и `warnings`. Рядом выводятся их расшифровки: `active_names`, `latched_names`, `warning_names`. Если причин несколько, они перечисляются через запятую; если нет — `none`.

`filter_samples` показывает, сколько отсчётов накоплено в фильтре. `measurement_unit` указывает единицы обработанного значения: `percent_x10` для насоса и `celsius_x10` для приточки. При `signal_valid=no` измерение нельзя считать рабочим, даже если числовое поле равно нулю.

Ручная подмена видна по `signal_injected=yes`, заданному `injected_value` и единицам `injected_unit`. Отдельно выводится `wire_break_injected`. Включённая имитация обрыва имеет приоритет перед ручным значением тока. После `inject signal off` источник снова переключается на модель датчика. Команда подтверждает принятие настройки сразу, а сами показания обновляются на следующем опросе.

В журнале после строки события выводятся его профиль, тип входа, исправность сигнала и названия причин. Это данные на момент события: последующая смена профиля или типа входа старую запись не меняет.

## Предупреждения и технологические защиты

Кроме исправности электрического входа контроллер проверяет само измерение: уровень насоса или температуру приточки. Есть четыре ограничения: `low-warning`, `high-warning`, `low-trip` и `high-trip`. Каждое имеет порог, гистерезис и задержку.

Предупреждение не меняет состояние и не останавливает привод. Оно появляется в `warnings` и в журнале как `WARNING`; после возврата в норму снимается автоматически с событием `WARNING_CLEARED`. Бит `0x1` означает нижнее предупреждение, `0x2` — верхнее. Эти биты относятся к отдельной маске предупреждений, а не к `active` и `latched`.

Авария переводит контроллер в `FAULT` и обнуляет выход. Нижнее ограничение имеет код `0x4`, верхнее — `0x8`. Причина снимается после возврата за границу гистерезиса, но авария остаётся в `latched` до ручного сброса. Сброс не запускает привод. С предупреждением пуск разрешён, с зафиксированной аварией — нет.

По умолчанию установлены такие параметры:

| Ограничение | Насос: порог / гистерезис | Приточка: порог / гистерезис | Задержка |
|---|---|---|---|
| Нижнее предупреждение | 10% / 2% | 5 °C / 1 °C | 500 мс |
| Верхнее предупреждение | 90% / 2% | 35 °C / 1 °C | 500 мс |
| Нижняя авария | 5% / 2% | 0 °C / 1 °C | 1000 мс |
| Верхняя авария | 95% / 2% | 38 °C / 1 °C | 1000 мс |

Для нижнего ограничения отсчёт задержки начинается при значении **не выше** порога. Если до срабатывания значение вернулось выше порога, таймер обнуляется. Уже сработавшее ограничение снимается при `порог + гистерезис`. Для верхнего ограничения всё зеркально: срабатывание при значении **не ниже** порога, снятие при `порог − гистерезис`. При нулевом гистерезисе для снятия нужно строго перейти на нормальную сторону порога.

Задержка считается по времени, а не по числу отсчётов. Проверка идёт по отфильтрованному измерению, поэтому сначала учитывается время установления фильтра. Обрыв и недопустимый ток или напряжение по-прежнему останавливают привод немедленно, без этих задержек. Неисправный вход прерывает незавершённые таймеры; уже активное ограничение снимается только по следующему исправному измерению.

Ограничения проверяются и в `READY`, и во время работы, и в `FAULT`. Это позволяет увидеть предупреждение до пуска и проверить исчезновение причины перед сбросом.

Настройки доступны через Shell, когда контроллер остановлен и нет зафиксированной аварии:

```text
protect show
protect set low-warning 450 20 300
protect set low-trip 400 20 800
protect disable high-warning
```

После имени идут порог в десятых долях, гистерезис в тех же единицах и задержка в мс. Здесь нижнее предупреждение настроено на 45%, гистерезис 2%, задержку 300 мс. Нижняя авария — на 40%, 2% и 800 мс. `set` также включает отключённое ограничение. Порог и граница снятия должны помещаться в шкалу профиля, задержка — в диапазон 0–60000 мс. Нулевая задержка означает срабатывание на первом подходящем отсчёте.

Пары уставок проверяются независимо: нижняя аварийная уставка должна быть строго ниже верхней аварийной, нижнее предупреждение — строго ниже верхнего предупреждения. Равенство и пересечение возвращают `-EINVAL`, настройки при этом не меняются. Проверка действует и для отключённых ограничений.

Изменения настроек сначала действуют только в RAM. Чтобы они пережили перезапуск, выполните `config save`. Смена профиля восстанавливает его значения защит по умолчанию; смена типа входа сохраняет настройки, но сбрасывает таймеры и фильтр.

## Сохранение настроек в NVS

На `qemu_cortex_m3` используется Zephyr Settings с backend NVS. Для эмулятора добавлена отдельная flash на semihosting: её содержимое находится в файле `controller_flash.bin` в рабочем каталоге QEMU. Программа и её flash-хранилище разделены; файл настроек не записывается поверх прошивки.

```text
config show
config save
config load
config erase
```

`save` сохраняет текущий профиль, тип входа, параметры PI и все четыре настройки защит, включая признаки отключения. Автоматической записи при каждом изменении нет. `load` загружает сохранённый набор целиком. `erase` удаляет запись из NVS, но оставляет текущие настройки в RAM; после следующего запуска будут дефолты. Все три команды разрешены только в `STOPPED` или `READY`.

При загрузке программы сохранённые настройки читаются автоматически. Привод остаётся остановленным и по-прежнему ждёт `start`. Аварии, журнал, интегратор, таймеры защит и инъекции не сохраняются.

Формат записи имеет версию и CRC32. В NVS сохраняется один блок: профиль, вход, PI и защиты. До применения проверяются длина, версия, контрольная сумма, коэффициенты, диапазоны и порядок уставок. Если блок повреждён или не поддерживается, он не применяется частично. При неудачной загрузке в начале работы остаются дефолты; при ручном `load` — предыдущие настройки. В `status` видны `settings_ready`, `settings_present` и `settings_error`.

Запуск через `west build -t run` использует файл в каталоге сборки. Для проверки сохранения завершите QEMU через `Ctrl+A`, `X` и запустите снова из того же каталога. Очистка каталога сборки (`build.py -c`) удалит и этот файл — это не перезапуск контроллера с сохранённой flash.

Semihosting нужен только для QEMU. На плате нужно заменить узел файловой flash в overlay разделом настоящей flash и включить Settings/NVS для этой платы. Формат записи и код сохранения остаются теми же.

Команды ниже рассчитаны на Ubuntu 24.04 x86_64. Выполнять из каталога проекта:

```bash

  cmake ninja-build gperf device-tree-compiler make curl xz-utils qemu-system-arm

git -C ../zephyr-workspace/zephyr remote add origin https://github.com/zephyrproject-rtos/zephyr
git -C ../zephyr-workspace/zephyr fetch --depth 1 origin 6848730b4b3f4d6e9151a0a8873955878be1a18d
git -C ../zephyr-workspace/zephyr checkout --detach FETCH_HEAD
west init -l ../zephyr-workspace/zephyr
```

## Запуск

```bash
python3 build.py -c -r
```

Скрипт очистит каталог сборки, соберёт приложение для `qemu_cortex_m3` и запустит QEMU. Можно сделать то же самое через West:

```bash
west build -b qemu_cortex_m3 -d build .
west build -d build -t run
```

Выход из QEMU: `Ctrl+A`, затем `X`.

## Проверка обрыва вручную

В консоли появится `uart:~$`. Сначала проверяем состояние и запускаем привод:

```text
status
start
status
```

Теперь включаем обрыв. Перед следующим `status` дайте контроллеру один цикл опроса — примерно 100 мс.

```text
inject wire-break on
status
events
```

В статусе должны быть `state=FAULT`, `active=0x1`, `latched=0x1`, ток `current_ua=2000` и выход `output_x100=0`. В журнале появится событие `FAULT` с причиной `faults=0x1`.

Попробуйте сбросить аварию до восстановления датчика:

```text
reset
```

Команда будет отклонена. Убираем обрыв:

```text
inject wire-break off
status
```

После следующего опроса `active` станет `0x0`, но состояние останется `FAULT`, а `latched` — `0x1`. Теперь можно выполнить сброс:

```text
reset
status
```

Контроллер вернётся в `READY`. Выход останется нулевым, пока снова не введём `start`.

Для смены профиля или типа входа:

```text
stop
set profile ahu
set mode 0-10v
status
```

### Журнал

Команда `events` показывает последние 32 события: номер, время от загрузки, состояние, причину аварии, ток, напряжение, обработанное измерение и задание частоты. Записи идут от старых к новым. Когда журнал заполняется, новые события вытесняют старые. Всё хранится в RAM, поэтому после перезапуска журнал пустой.

## Тесты

Для исходников приложения включены `-Wall -Wextra`. Тесты отдельно проверяют повторный отказ пуска без утечки мьютекса, десять тактов насыщения PI и пуск после долгого простоя.

```bash
python "$ZEPHYR_BASE/scripts/twister" -T tests -p qemu_cortex_m3 -O twister-out -j 4
python scripts/demo_test.py --elf build/zephyr/zephyr.elf
```

Через Twister запускаются тесты масштабирования, фильтра, границ входного сигнала, состояний, ограничения частоты и журнала. Отдельный системный тест проходит весь аварийный сценарий с периодическим опросом датчика и проверкой выхода. Он проверяет, что останов происходит не позднее 150 мс после инъекции. Это результат для QEMU; на плате время реакции нужно будет измерить заново.

`demo_test.py` запускает собранное приложение в QEMU и вводит команды через UART, как при ручной проверке выше. Он также проверяет журнал и убеждается, что сброс не запускает привод. Протокол остаётся в `build/demo-test.log`.

Отдельные тесты проверяют единичный выход тока или напряжения за границу при уже заполненном фильтре. Даже с задержками технологических защит в 60 секунд команда приводу должна стать нулевой после первого аварийного отсчёта; нормальный следующий отсчёт не должен сам снять зафиксированную аварию.

Те же проверки выполняются в GitHub Actions. Логи и результаты можно скачать из артефакта `qemu-test-results`.

## YAML-сценарии

Сценарии находятся в `scenarios/controller.yaml`. Это команды Shell и ожидаемые результаты, которые выполняются на собранном приложении в QEMU:

```bash
python -m scripts.run_scenarios --elf build/zephyr/zephyr.elf
python -m scripts.run_scenarios --elf build/zephyr/zephyr.elf --scenario nvs_restart_and_erase
python -m scripts.test_storage --elf build/zephyr/zephyr.elf
python -m unittest discover -s tests/host -p 'test_*.py'
```

Минимальный пример:

```yaml
version: 1
scenarios:
  - name: current_overrange
    steps:
      - command: start
        expect: [OK]
      - command: inject signal 25000
        expect: [OK]
      - status: {state: FAULT, active: 2, latched: 2, output_x100: 0}
      - command: reset
        expect: ["Команда отклонена: -16"]
```

Здесь 25 мА — выход за диапазон (`INPUT_RANGE`, код `0x2`). Для обрыва (`WIRE_BREAK`, `0x1`) используется 2 мА. Проверки не смешивают эти причины.

`status` отдельно показывает `sensor_faults` (обрыв и диапазон входа) и `process_faults` (технологические защиты). Поле `active` — их побитовое объединение. Общая фиксация `latched` и ручной сброс остаются прежними.

Сценарий `nvs_corrupted_crc_restores_defaults` сохраняет изменённые настройки и выполняет `corrupt_settings_crc: true`. Этот шаг останавливает QEMU, портит CRC приложения в изолированном файле flash, пересчитывает внешнюю CRC NVS и запускает QEMU снова. Сценарий проверяет дефолтный профиль, вход, PI и защиту, нулевой выход и ошибку `-EBADMSG`. Для шага нужна ровно одна сохранённая запись версии 1; неоднозначный образ считается ошибкой теста.

Шаг `status` ждёт совпадения полей, по умолчанию до 2000 мс. Значение `timeout_ms` можно задать рядом с `status`. Шаг `wait_ms` добавляет паузу, `restart: true` полностью перезапускает процесс QEMU с той же flash. Для `command` обязателен непустой список ожидаемого текста. Неправильные поля, повторяющиеся ключи YAML, пустые сценарии и неизвестное имя сценария завершают прогон с ошибкой.

Каждый сценарий получает отдельный временный каталог flash. Перезапуски внутри одного сценария используют один файл, а между сценариями настройки не переносятся. Обычный `demo_test.py` тоже запускается с изолированной flash, поэтому тесты не портят сохранённые вручную настройки. Сценарий NVS проверяет восстановление профиля, входа, защит и признака отключения, запрет работы с хранилищем во время пуска, отсутствие автопуска и удаление записи. Дополнительный прогон проверяет недоступную flash и повреждение сохранённого блока.

Протоколы сохраняются в `build/scenarios.log` и `build/storage-test.log`. GitHub Actions выполняет эти проверки и сохраняет протоколы вместе с результатами Twister.

## Что менять при переносе на плату

Логика находится в `src/controller.c`: состояния, ПИ-регулятор, защита и журнал. Для синхронизации этот файл использует мьютекс Zephyr. В `src/controller_app.c` находятся периодический опрос и синхронизация с Shell.

Работа с устройствами вынесена в `include/controller_io.h`. Для QEMU используется `src/io_sim.c`, для аппаратного ввода — `src/io_hw.c`. Пример ADC для nRF52840 DK описан ниже. Реальный выход на привод нужно реализовать под выбранный интерфейс.

Выбор аппаратного ввода выполняется через `CONFIG_USE_HW_IO`. Его функции инъекции возвращают `-ENOTSUP`.

Пока реализованы защиты от обрыва токовой петли и выхода сигнала за допустимый диапазон. Modbus, аппаратной STO и проверки на реальном оборудовании здесь ещё нет.


## Аппаратный watchdog

Вариант `mps2/an385` запускает CMSDK watchdog с полным временем до сброса 2000 мс. Для него включены `CONFIG_WATCHDOG` и `CONFIG_APP_WATCHDOG`, устройство выбирается по alias `watchdog0`. Сборка `qemu_cortex_m3` остаётся без WDT: у LM3S6965 в этой конфигурации Zephyr нет доступного драйвера watchdog. Команда `crash_test` в ней возвращает `-ENOTSUP`.

```bash
west build -b mps2/an385 -d build-watchdog .
west build -d build-watchdog -t run
```

После загрузки появляется `Watchdog armed: timeout_ms=2000 reset=SOC`. В Shell выполните `start`, затем `crash_test`. Команда выставляет атомарный флаг; на следующем цикле сам поток `main` засыпает навсегда. Shell продолжает работать, но основной цикл больше не кормит watchdog. Примерно через две секунды SoC перезапускается. Сохранённые настройки загружаются из NVS, выход остаётся выключенным, для работы нужен новый `start`. На реальной плате состояние выхода во время зависания и reset дополнительно определяется схемой и драйвером выхода.

`wdt_feed()` вызывается только потоком `main` после возврата из `controller_app_tick()`: чтение входа, `controller_update()` и запись выхода уже завершены. Активная технологическая авария считается успешно обработанным циклом и не вызывает перезагрузку. В таймере, ISR, Shell и обработчике NMI кормления нет. При ошибке инициализации цикл не запускается; при ошибке кормления поток прекращает работу и ждёт аппаратного сброса.

CMSDK-драйвер в закреплённой версии Zephyr отсчитывает два одинаковых окна: первое вызывает NMI, второе — аппаратный reset. Поэтому для этого драйвера устанавливается окно 1000 мс, чтобы полное время до reset составляло 2000 мс. Callback не задан, обработчик NMI драйвера не перезаряжает счётчик. Для остальных драйверов окно API составляет 2000 мс. `WDT_FLAG_RESET_SOC` включает сброс системы, `wdt_setup(..., 0)` оставляет watchdog работающим во время сна.

Автоматическая проверка:

```bash
python -m scripts.test_watchdog --elf build-watchdog/zephyr/zephyr.elf
```

Тест проверяет нормальную работу дольше тайм-аута, затем дважды вызывает `crash_test`. Он ждёт новое сообщение загрузки в том же процессе QEMU, проверяет время сброса, восстановление NVS, очистку журнала и нулевой выход. Результат сохраняется в `build-watchdog/watchdog-test.log`, проверка включена в Actions.

Для реальной платы включите её WDT в devicetree, назначьте alias `watchdog0` и включите `CONFIG_WATCHDOG=y`, `CONFIG_APP_WATCHDOG=y`. Проверьте доступный диапазон тайм-аутов и особенности выбранного драйвера. API контроллера вызывается из потока; для кормления WDT отдельный поток не нужен.


## Аппаратный вход ADC

`CONFIG_USE_HW_IO=y` выбирает `src/io_hw.c`, иначе собирается `io_sim.c`. Готовый пример — `nrf52840dk/nrf52840`; его board-конфигурация включает аппаратный ввод. QEMU по умолчанию использует симулятор. На DK выход на привод пока не подключён: `controller_io_write()` ничего не включает, `controller_io_output()` возвращает 0. Для управления приводом нужна отдельная реализация выхода под выбранный интерфейс.

```bash
west update hal_nordic
west build -b nrf52840dk/nrf52840 -d build-hw .
```

В `boards/nrf52840dk_nrf52840.overlay` заданы два канала SAADC с разрешением 12 бит:

| Вход | Вывод DK | Внешняя цепь | Пересчёт |
| --- | --- | --- | --- |
| 4–20 мА | AIN0 / P0.02 | Шунт 125 Ом | `current_ua = adc_mv * 1000 / 125` |
| 0–10 В | AIN1 / P0.03 | Делитель: 30 кОм сверху, 10 кОм на землю | `voltage_mv = adc_mv * 4` |

Это пример схемы согласования, не разрешение подавать 10 В прямо на ADC. Для реального входного модуля нужны защита входа, соблюдение допустимого напряжения на выводе и общий опорный потенциал либо развязка. Параметры `current-shunt-ohms` и `voltage-divider-multiplier` должны соответствовать вашей цепи. Точность зависит от шунта, делителя и опоры ADC. Обрыв 4–20 мА определяется по току; на входе 0–10 В нулевое напряжение допустимо, поэтому отличить его от обрыва без дополнительной схемы нельзя.

Вызовы `adc_channel_setup_dt()` и `adc_read()` выполняются в отдельном рабочем потоке. Основной цикл ждёт завершения запроса не более 20 мс; захват замка самого модуля использует `K_NO_WAIT`. Даже если драйвер застрял на внутреннем замке, поток контроллера получает `-ETIMEDOUT`. После тайм-аута запрос и буфер остаются во владении рабочего потока до завершения ADC. Поздний результат отбрасывается; новый запрос не запускается поверх старого. Если драйвер не завершился вообще, последующие чтения возвращают тайм-аут без ожидания. Желательно выделить ADC этому модулю, чтобы другие потребители не мешали опросу. Вызовы API ввода допустимы только из потока; рабочий поток ADC не кормит watchdog.

`controller_io_read()` теперь возвращает код результата. Исправный вход — 0; ошибка ADC, преобразования или диапазона — `-EIO`; превышение времени — `-ETIMEDOUT`; неподдерживаемый режим и команды инъекции на аппаратном backend — `-ENOTSUP`. При выходе физического сигнала за диапазон отсчёт сохраняется для штатных защит. При ошибке получения отсчёта поле `read_error` ненулевое, контроллер немедленно фиксирует `INPUT_IO`, сбрасывает фильтр и останавливает выход. В `status` видны код `read_error` и причина `INPUT_IO`; для возобновления нужны исправный вход, `reset` и отдельный `start`.

Twister запускает `tests/io_hw` с драйвером ADC Emulator, но с настоящим `io_hw.c`: проверяются единицы, диапазоны, насыщение ADC, ошибка драйвера, задержанное завершение и восстановление после тайм-аута. В Actions дополнительно проверяется сборка DK. Измерения и электрику на самой плате эти тесты не заменяют.
